IAM-811 Machine Learning y Aprendizaje Profundo

Laboratorio Final de Hito: Sistema Inteligente de Control de Peaje

Entrega: 25/11/26 100 puntos + hasta 20 adicionales

1. Descripción

En este laboratorio integrarán lo trabajado durante el hito en un sistema real de punta a punta: un sistema de control de peaje que identifica vehículos a partir de video capturado con una aplicación móvil.

El sistema reutiliza el modelo de detección de placas de proyectos anteriores y lo combina con un modelo de segmentación de instancias y uno de keypoints. La inferencia corre en la nube (RunPod o Google Colab), y una aplicación web publicada en un subdominio integra todas las rutas, APIs y un agente conversacional que responde consultas sobre placas por texto o imagen. La aplicación web recibe en tiempo real cada vehículo registrado por las casetas, y el acceso al sistema se hace con autenticación de Google.

2. Objetivos

Objetivo general

Desarrollar e implementar un sistema de control de peaje basado en visión por computadora, que integre tres modelos de deep learning, una aplicación móvil, una aplicación web en tiempo real con autenticación de Google y un agente conversacional, usando infraestructura en la nube y sin depender de recursos locales.

Objetivos específicos

  1. Reutilizar el modelo de detección de placas de proyectos anteriores e incorporar OCR para leer el texto de la placa.
  2. Entrenar un modelo de segmentación de instancias que clasifique el tipo de vehículo (moto, auto, minibús, camión, bus) para determinar la tarifa.
  3. Entrenar un modelo de keypoints sobre las ruedas del vehículo para estimar el número de ejes.
  4. Gestionar los datasets en Roboflow y entrenar los modelos en Google Colab.
  5. Servir los tres modelos en un único endpoint de inferencia en RunPod o Google Colab.
  6. Desarrollar una aplicación web publicada en un subdominio que integre rutas, API REST, base de datos y el agente conversacional.
  7. Implementar la actualización en tiempo real del panel web con cada vehículo registrado.
  8. Implementar autenticación con Google (OAuth 2.0) en la aplicación web y la aplicación móvil.
  9. Desarrollar una aplicación móvil que capture video y consuma la API del sistema.
  10. Implementar un agente conversacional que, a partir de una placa en texto o imagen, informe su estado en el sistema.

4. Componentes mínimos obligatorios

4.1 Aplicación móvil

  • Inicio de sesión con Google (Google Sign-In).
  • Modo Caseta: captura video y envía frames (2 a 5 fps) o clips cortos (5 a 10 s) a la API. Muestra la placa leída, la categoría, los ejes, la tarifa y el estado.
  • Modo Consulta: permite enviar al agente una foto de una placa o escribir la placa en texto.
  • Tecnología libre: Kotlin, Java, Flutter, React Native, Ionic, etc.

4.2 Aplicación web (en subdominio)

  • Publicada en un subdominio accesible por HTTPS.
  • Tecnología libre: Laravel, Django, Flask, FastAPI, React, Vue.js, Angular, Next.js, Node/Express, u otra.
  • Puede estar en VPS u hosting compartido.
  • Páginas mínimas:
    Panel en tiempo real: pasos, recaudación y alertas Vehículos: CRUD Pasos: historial con imagen de evidencia Alertas Chat: agente conversacional Estado: indica si el endpoint de inferencia responde
  • El backend genera una alerta cuando se detecta una placa no registrada o sin saldo.

4.3 Registro en tiempo real

Cada vez que una caseta (app móvil) registra un vehículo, el panel web debe mostrarlo de inmediato, sin recargar la página: placa, imagen de evidencia, categoría, ejes, monto, estado y hora. Lo mismo aplica a las alertas y a los contadores de recaudación.

Tecnologías sugeridas, a elección del grupo:

  • WebSockets: Laravel Reverb o Pusher, Django Channels, Socket.IO, etc.
  • Server-Sent Events (SSE).
  • Servicios gestionados: Pusher, Ably, Firebase Realtime Database o Firestore.
Si usan hosting compartido, verifiquen que soporte conexiones persistentes. Si no las soporta, usen un servicio gestionado (Pusher, Ably o Firebase).

4.4 Autenticación con Google

  • El acceso a la aplicación web y a la aplicación móvil se hace exclusivamente con Google (OAuth 2.0 / Google Sign-In). No se permiten usuarios con contraseña propia.
  • La aplicación debe manejar al menos dos roles:
    • Administrador: gestiona vehículos, tarifas y casetas.
    • Operador: registra pasos y consulta placas.
  • Solo las cuentas de Google autorizadas (lista blanca en la base de datos) pueden ingresar. Las demás deben ver un mensaje de acceso denegado.
  • La API valida el token de Google (o un token propio emitido tras el inicio de sesión con Google) en cada petición de la app móvil.
  • La cuenta de Google del docente debe estar autorizada con rol de administrador. El correo se indicará en la plataforma de entrega.

4.5 API REST mínima

Método Ruta Descripción
POST /api/v1/auth/google Recibe el token de Google desde la app y devuelve el token de sesión del sistema
POST /api/v1/pasos/frame Recibe un frame desde la app, llama a la inferencia, registra el paso y lo emite en tiempo real
POST /api/v1/placas/consultar Consulta una placa por texto y devuelve su estado
POST /api/v1/placas/consultar-imagen Consulta una placa por imagen (M1 + OCR) y devuelve su estado

La API debe estar documentada (Swagger/OpenAPI, Postman o equivalente) y todas las rutas, excepto /auth/google, deben exigir autenticación.

4.7 Modelos de inferencia

Modelo Tarea Uso en el peaje
M1 Detección de placas (proyecto anterior) + OCR (EasyOCR, PaddleOCR u otro) Identificar el vehículo
M2 Segmentación de instancias (YOLO-seg) Categoría del vehículo → tarifa
M3 Keypoints (YOLO-pose) sobre las ruedas Número de ejes → tarifa de vehículos pesados

M1: Detección de placas + OCR. El modelo localiza la placa, se recorta la región y el OCR extrae el texto, que luego se normaliza (mayúsculas, sin guiones ni espacios).

M2: Segmentación de instancias. Cada vehículo recibe su propia máscara y una categoría (moto, auto, minibús, camión, bus). La categoría define la tarifa base.

M3: Keypoints de ruedas. El modelo ubica un keypoint en el centro de cada rueda visible desde un lado del vehículo. El número de keypoints corresponde al número de ejes, que define la tarifa de los vehículos pesados.

  • M2 y M3 deben entrenarse con un dataset propio etiquetado en Roboflow. Se permite partir de datasets de Roboflow Universe, pero deben ampliarlos con imágenes propias.
  • Los tres modelos deben servirse desde un único endpoint que devuelva JSON con: placa, confianza, categoría, ejes y latencia.

Las imágenes son referenciales. Los resultados reales dependerán del dataset y del entrenamiento de cada grupo.

4.8 Agente conversacional

Recibe una placa por texto o por imagen y responde con uno de estos cuatro estados:

Estado Condición
Registrada y con paso La placa está registrada y tiene pasos (indicar fecha, caseta, categoría y monto)
Registrada sin paso La placa está registrada pero nunca pasó por el peaje
Identificada no registrada La cámara la detectó pero no está registrada (posible evasión)
No existe No hay ningún registro de la placa

Requisitos del agente:

  • Disponible solo para usuarios autenticados con Google.
  • Responde solo con datos obtenidos de la base de datos o la API, sin inventar información.
  • Normaliza la placa antes de buscar: mayúsculas, sin guiones ni espacios, validación de formato.
  • Ante errores probables de OCR (O↔0, I↔1, B↔8, S↔5), sugiere coincidencias cercanas ("¿Quisiste decir…?").
  • Si la imagen no tiene una placa legible, lo indica y pide otra imagen.
  • Puede implementarse con function calling desde el backend, con un framework de agentes (LangChain, LlamaIndex u otro) o con un LLM propio (por ejemplo, Ollama en RunPod).
